# Rust Best Practices — Model Council Synthesis

Council consulted: **Claude Fable 5**, **GPT 5.5**, **Gemini 3.1 Pro**. (Requested Grok 4.5 and GLM 5.2 are not currently available as council subagents; GPT 5.5 stands in for GPT-5.6 Sol.)

The organizing thesis all three converge on: **at the expert level, Rust best practices are the discipline of moving every implicit contract — safety, cancellation, semver, supply chain, panic-vs-error, MSRV — into a place the toolchain can mechanically check.** Where they diverge is on *how* deeply to go in each dimension and which failure modes matter most.

## Where Models Disagree

| **How prescriptive should the blocking rule be?** | Cite Alice Ryhl's **10–100 µs quantitative rule** verbatim with a decision table (spawn_blocking / rayon / dedicated thread by workload type) | Prefer stdlib `Mutex` for short sync critical sections; qualitative guidance without a µs threshold | Not addressed explicitly | Fable weights Tokio-maintainer prescriptive numbers; GPT gives compositional guidance grounded in stdlib docs; Gemini omits blocking entirely |
| **How much verification is enough?** | A **six-rung ladder**: clippy → proptest → insta → structure-aware fuzzing with `arbitrary` → Miri → Loom, matched to bug classes | Roughly the same tools but flatter: unit + integration + proptest + insta + cargo-fuzz + Miri, as a suite rather than a hierarchy | Minimal — Miri emphasized; property testing / fuzzing not called out | Fable frames verification as *layered enforcement by bug class*; GPT frames it as *tool coverage of surfaces*; Gemini treats it as a lower priority than architectural discipline |
| **How central is `cargo-vet`/supply chain?** | **Central** — argues audits are the difference between "we ran a scanner" and "chain of custody" | Uses `cargo-deny` + `cargo-audit` + RustSec advisories; mentions `cargo-vet`-style thinking only implicitly | `cargo-audit` + `cargo-deny` for policy; no `cargo-vet` | Fable treats supply-chain as a first-class practice for distributed-systems shops; GPT treats it as a CI stage among many; Gemini treats it as basic hygiene |
| **Which semver hazards deserve top billing?** | Sealed-trait *implementability itself* is public API; `cargo-semver-checks` as a mandatory pre-publish gate | Enumerates a **long catalog** from the Cargo reference: adding fields, adding variants without `#[non_exhaustive]`, tightening bounds, adding inherent methods (trait-method collision), RPIT capture, changing MSRV | Sealed traits per C-SEALED; newtypes hide representation (C-NEWTYPE-HIDE) | Fable focuses on the *machine-check-in-CI* end; GPT compiles the exhaustive *human-review checklist* from Cargo's own SemVer reference; Gemini gives the two headline patterns |

|---|---|---|

| Claude Fable 5 | **Alice Ryhl's 10–100 µs rule** as a hard numeric threshold, with a spawn_blocking / rayon / dedicated-thread decision table by workload. | Claude Fable 5 | **Sealed traits as a capability matrix** (implement / call / override) from Predrag Gruevski, with the deeper claim that *trait implementability itself is semver-relevant public API* and should be enforced with `cargo-semver-checks` in CI. | Reframes sealing from a binary yes/no to a design menu, and makes semver a mechanical check rather than a review-time vibe. |
| Claude Fable 5 | **Structure-aware fuzzing with the `arbitrary` crate + Loom for lock-free code**, as distinct rungs of a verification ladder aligned to specific bug classes (parser front-gate escape, memory-model reordering). | Names bugs neither Miri nor property tests can catch — critical for anyone writing custom sync primitives or protocol parsers. |
| Claude Fable 5 | **GreptimeDB's stacked per-layer error pattern** for large multi-crate systems — each crate defines its own small error, wrapping the layer below as an opaque source. | A concrete counterpoint to the "one big enum" anti-pattern that emerges when `thiserror` scales past a single crate. |
| GPT 5.5 | **Fallible `Drop` doctrine** — provide explicit `close`/`finish`/`shutdown`; `Drop` runs during panic and a failing destructor aborts. | Prevents a specific class of production outage where "cleanup during shutdown" silently aborts the process. |
| GPT 5.5 | **FFI as a first-class expertise dimension** — `Option<extern "C" fn>` for nullable function pointers using the null-pointer optimization, `-unwind` ABI selection to decide whether panics may cross the boundary. | For infrastructure/AI-native work that binds to C libraries (llama.cpp, CUDA, ONNX Runtime, DB drivers), these are exactly the details that produce "impossible" segfaults. |
| GPT 5.5 | **Additive-features discipline** — model `no_std` as a `std` default feature (not the inverse); removing a default feature is a breaking change; hide optional deps behind semantic names with `dep:`. | Feature-flag design is a hidden semver surface most teams get wrong; GPT is the only model to give a coherent set of rules. |

## Comprehensive Analysis

**High-confidence findings.** Across three independent models drawing on distinct source sets, ten specific practices converge — this is the reliability floor. Split your error strategy by audience (`thiserror` for library contracts, `anyhow` for application glue, `miette` for humans). Push invariants into types via typestate, newtypes, and sealed traits, using the standard C-SEALED and C-NEWTYPE patterns from the API Guidelines. In async code, never hold a lock guard across `.await`, prefer `std::sync::Mutex` for short sync critical sections, and reach for `tokio::sync::Mutex` only when awaiting under the lock is genuinely required. Every `unsafe` block gets a `// SAFETY:` comment; every unsafe function documents its contract; Miri runs in CI for anything containing `unsafe`. Use a flat workspace layout with a virtual root, inherit dep versions via `[workspace.dependencies]`, and enforce `cargo fmt --check`, `cargo clippy -Dwarnings`, `cargo-deny`, and `cargo-audit` in CI, with `cargo-semver-checks` before every publish. Declare and CI-test `rust-version`, and migrate to the 2024 edition deliberately — auditing RPIT lifetime capture, `unsafe extern` blocks, and `static mut` references as you go. Treat these as non-negotiable; they represent independent sourcing to the Rust API Guidelines, Rust Reference, Cargo docs, Tokio docs, matklad, Cliff Biffle, and Ralf Jung's Miri work.

**Areas of divergence and how to weigh them.** The three models split most interestingly on *which async failure mode deserves top billing*. Claude Fable 5 makes the sharpest argument that **implicit cancellation** is the deepest, most under-taught problem in production async Rust — with Tokio's own docs enumerating the cancellation-unsafe primitives and a distinct bug class where you lose queue position rather than data. This is well-cited from primary sources and matches actual field experience with `tokio::select!` bugs. GPT 5.5 takes a broader systems-engineering view centered on scheduler semantics, runtime boundaries, and the API-Guidelines rule that fallible cleanup belongs in `close()`/`finish()`, not `Drop`. Gemini 3.1 Pro foregrounds the `Send`-bound problem and async-trait overhead — real, but a shallower dimension than cancellation and one the language is already fixing with `trait_variant` and RFC 3654 return-type notation. **My weighting: adopt Fable's cancellation-safety discipline as the top async priority**, GPT's runtime/lock/drop discipline as the second layer, and treat the `Send`-bound issue as a solved-in-progress language problem rather than a permanent best practice. The models also diverge on verification depth: Fable's six-rung ladder (clippy → proptest → insta → structure-aware fuzzing → Miri → Loom) matched to bug classes is the most useful framing, and GPT's version is a subset of it. Gemini de-emphasizes verification beyond Miri, which is a genuine weakness of that report. Finally, on supply chain, Fable's argument for `cargo-vet` — audit records, not just CVE scanning — is the strongest position and worth adopting if your organization ships Rust to production; GPT and Gemini stop at `cargo-audit`/`cargo-deny`, which is the minimum floor.

**Unique insights worth banking.** Three findings from single models deserve to be integrated into your practice regardless of the majority signal. First, **Alice Ryhl's 10–100 µs blocking threshold** (from Fable) turns a fuzzy heuristic into a measurable rule and explains the specific dev-passes-prod-fails failure mode that catches most teams. Second, **GPT 5.5's FFI section** is uniquely thorough — `Option<extern "C" fn>` for nullable function pointers, `-unwind` ABI selection, and `#[unsafe(no_mangle)]` as a linker-global invariant — and directly relevant to any Rust code binding to C-heavy AI/ML libraries. Third, **GreptimeDB's per-layer stacked error pattern** (from Fable) is the answer to the "our `thiserror` enum has grown to 200 variants" scaling problem — layer boundaries define error boundaries. Also worth noting: GPT alone flags that **virtual workspaces must set the resolver explicitly** in 2024, which is a specific edition-migration bug you will otherwise hit silently.

**Recommendation for your stack.** For distributed systems and AI-native applications specifically, the priority order is: (1) audit every `select!` and `timeout` for cancellation safety and route CPU work off the executor at the 10–100 µs threshold; (2) adopt the SAFETY-comment policy plus Miri in CI for any unsafe, and `#![forbid(unsafe_code)]` in everything else; (3) split errors by audience and adopt stacked per-layer errors once you cross ~2 crates worth of variants; (4) put semver, MSRV, supply chain (`cargo-deny` + `cargo-vet` if you can), and unused-dep detection behind machine checks in CI, not review-time vibes; (5) migrate to the 2024 edition deliberately, treating RPIT capture changes as semver events; (6) use the flat `crates/` workspace layout with `[workspace.dependencies]` inheritance and `cargo xtask` for automation. The through-line all three models converge on is the right one: **expert Rust is the practice of making every implicit contract explicit and mechanically checked**, so that ownership, cancellation, safety, semver, and supply-chain trust become failing CI jobs rather than production incidents.
