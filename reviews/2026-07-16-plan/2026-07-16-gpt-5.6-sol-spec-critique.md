# Adversarial critique of the phase-1 factory spec

*2026-07-16. Reviewer: GPT 5.6-Sol xhigh. Target: `SPEC.md` at commit `3e7a76b`.*

## Verdict

Do not build phase 1 from this spec yet. The product boundary is good - narrow named skills, deterministic deny rules, an evidenced PR as the autonomy limit, and an unchanged production deploy gate - but the execution and state boundaries do not enforce the safety claims.

Five issues are build blockers:

1. The interactive worker still has the orchestration session's fleet credentials and external channels.
2. The upload-processing dashboard runs as `conductor`, which can read the 1Password service token and owns fleet SSH material.
3. Runtime requests, workflow state, and the ledger are mixed into a Git checkout without locking, idempotency, retention, or privacy boundaries.
4. The preview, screenshot, CI, and PR-evidence sequence cannot be implemented as written against the current tooling.
5. A PR opened with Jacob's existing PAT cannot be approved by Jacob, while the actual branch rule does not enforce the stated engineering-plus-owner gate.

These are not phase-2 refinements. They are prerequisites for safely processing even a manually triggered request. If a ruling requires the unsafe version, amend the ruling. `SPEC.md:14-17` cannot make a contradictory ruling correct by definition.

## Blocking findings

### 1. A human trigger does not make untrusted content safe

`SPEC.md:26-29` explicitly defers the credential-free worker/publisher split. `SPEC.md:49-52` then treats subagent tool allowlists as containment, and `SPEC.md:74-85` runs implementation and verification inside a normal orchestration session.

That violates the factory constitution's own lethal-trifecta rule. The phase-1 process has:

- private data and fleet credentials in the `claude-orchestrator` environment;
- untrusted email, screenshots, OCR, source comments, filenames, and test output;
- external channels through GitHub, network access, SSH, MySQL, and the model provider.

The synthesis says a human "vouches for the input at time zero." A human can confirm that the Owner sent the screenshot. A human cannot establish that the image contains no prompt injection, that a repository comment is benign, or that a test fixture cannot exploit a tool-using model. Trigger provenance and content trust are different properties.

The A37 tool restrictions are not enforcement:

- `factory-implement` has unrestricted Bash. It can read outside the worktree, inspect environment variables, call `ssh`, `mysql`, `gh`, `curl`, or modify the verifier.
- `factory-verify` also has Bash. Removing Edit and Write tools does not make Bash read-only; shell redirection, `sed -i`, `perl`, PHP, and ordinary commands can modify files.
- A prompt saying "worktree-scoped" is policy text, not an operating-system boundary.

An adversarial screenshot only needs to persuade the implementer to run something like `env`, read `/etc/orchestration/op.env`, or upload a file through `gh`. The current `conductor` account can read `/etc/orchestration/op.env`, owns `/var/lib/conductor/.ssh`, and has the Fieldbook API and database credentials injected into interactive sessions.

Required revision:

- Move a minimal worker/publisher split into phase 1.
- Run implementation in a disposable container or dedicated unprivileged user with the request mounted read-only and one worktree mounted read/write.
- Give the worker no SSH directory, no 1Password token, no DB/Fieldbook/GitHub credentials, no Docker socket, and no private-network access.
- Restrict model traffic to a short-lived, cost-capped credential or gateway token.
- Terminate the worker before tests run. Apply its patch in a clean verifier environment with no model credential.
- Run verification against a read-only worktree or record and compare the tree hash before and after verification.
- Let a deterministic outer publisher perform Git and GitHub mutations from the verified patch.

If that is ruled out for phase 1, phase 1 must remain shadow-only: produce an investigation and patch for a human to inspect, but do not automatically execute repository tests or publish from untrusted request content.

### 2. The dashboard must not run as `conductor`

`SPEC.md:118-124` places a new multipart-upload web application under `conductor`. That account is the wrong security principal for a parser exposed to user-controlled titles, Markdown, filenames, and image bytes.

On this host, `conductor` can read the 1Password service-account environment file and owns the fleet SSH directory. A path traversal, image-decoder flaw, template mistake, command-injection bug, unsafe `gh` invocation, or dependency RCE in the dashboard becomes a fleet compromise. Binding to `127.0.0.1` and putting Caddy in front reduces internet exposure; it does not reduce the process's local authority after compromise.

Required revision:

- Run the dashboard as a new `factory-web` user with no login shell, no SSH directory, no access to `/etc/orchestration/op.env`, no access to `env.tpl`, and no repository credentials.
- Give it write access only to a dedicated intake spool and its SQLite database/artifact directory.
- Use a Unix socket owned by `caddy:factory-web`, or add an authenticated Caddy-to-app assertion. A loopback TCP listener plus a trusted plain header can be spoofed by another local process.
- Add systemd hardening: `NoNewPrivileges=yes`, `PrivateTmp=yes`, `ProtectSystem=strict`, `ProtectHome=yes`, `ProtectKernelTunables=yes`, `ProtectControlGroups=yes`, `RestrictAddressFamilies=`, `CapabilityBoundingSet=`, and explicit `ReadWritePaths=`.
- Have the interactive supervisor claim sanitized requests from the spool. Do not make the web process a Git operator.

### 3. Markdown files in a source checkout are not a safe workflow ledger

`SPEC.md:41-43`, `SPEC.md:92-94`, `SPEC.md:129-133`, and `SPEC.md:186-190` make the private repository simultaneously:

- application source;
- request and attachment storage;
- mutable workflow state;
- audit ledger;
- deployment checkout.

This design fails under ordinary concurrency, not only attack:

- Two engineers can claim the same request and both pass the open-PR count before either creates a PR.
- A dashboard write can race a Git pull, checkout, commit, or queue move.
- A crash can leave a partial `request.md`, attachment, or `runs.md` row.
- Appending one Markdown table has no transaction spanning branch creation, PR creation, and ledger update.
- The dashboard derives state from mutually inconsistent snapshots of the filesystem, Markdown, and GitHub.
- Runtime queue writes leave the application checkout dirty and can block updates or accidentally enter an application commit.
- Mixing `rulings-*` and software requests in one `queue/` namespace invites misrouting.

It also creates a privacy and retention problem. `SPEC.md:86-94` requires request text verbatim, and the golden fixture uses a raw email plus screenshots. If queue contents and attachments enter the factory repository's audit history, employee or customer information becomes permanent Git history. A later 90-day deletion policy cannot remove it without history rewriting, which fleet policy forbids.

SQLite is not premature infrastructure here. It is the smallest correct implementation of request IDs, unique message/request fingerprints, stage transitions, leases, timestamps, PR uniqueness, and crash recovery.

Required revision:

- Move SQLite into phase 1 for requests, runs, events, artifacts, locks/leases, and PR state.
- Store raw request artifacts under `/var/lib/patchyard/artifacts/<id>/` with restrictive permissions and a retention policy. Store hashes and redacted/distilled metadata in the ledger.
- Keep code, policy, fixtures, and schemas in Git. Do not commit live requests or screenshots.
- Separate `requests` and `rulings` namespaces even if both are represented in the UI.
- Use atomic state transitions and uniqueness constraints for request ID, request fingerprint, branch, and PR number.

If A40 is intended to require raw requests in Git, A40 should be amended before implementation.

### 4. The evidence pipeline does not match the current preview and browser tooling

`SPEC.md:79-91` requires preview screenshots, extracted DOM order, CI evidence, and before/after images before the stage stops. Several required mechanisms do not exist or are out of order:

- The current status-dashboard preview driver creates editable previews. Its code no longer exposes a frozen-preview creation path, despite older documentation describing one.
- Editable previews follow a branch, not an immutable evidence SHA, and the shared `fieldbook_preview` database is mutable across all slots.
- `/opt/headless/render.py` cannot set the Fieldbook bearer header or establish Google OAuth. As written, an automated visit to an internal preview page will capture the login page.
- The helper accepts arbitrary `--eval` JavaScript and `--click` selectors but has no request-specific allowlist, redacted header file, output-size limit, or proof of the checked commit.
- The spec defines no factory slot lease, owner, TTL, cleanup, or collision behavior.
- `gh pr create` cannot upload local screenshots into the PR body. The spec does not say where evidence is stored or how a reviewer accesses it.
- Full GitHub CI does not exist until after the PR is opened. `SPEC.md:86-91` asks the initial PR creation step to include a CI link and then stop, with no wait, reconciliation, body update, or ready-for-review transition.

Required revision:

1. Define a draft-PR lifecycle: publish verified local patch as draft, wait for GitHub CI, capture preview evidence at the exact head SHA, update the evidence record, then mark ready and request review.
2. Add a factory preview allocation API/CLI with `owner`, request ID, expected SHA, created time, expiry, and guaranteed cleanup.
3. Verify `git rev-parse HEAD` in the preview before and after browser checks.
4. Keep phase-1 preview actions read-only because all slots share one mutable database.
5. Extend the headless helper to accept an owner-only header file, use the dev-fleet bearer header, redact it from logs, and limit navigation to the allocated preview host.
6. Define an authenticated artifact store or dashboard evidence route. Do not commit screenshots to the Fieldbook branch. GitHub can link to the evidence page even if it cannot render the protected image inline.
7. Make CI/network failures explicit states with timeouts and fail-closed behavior.

Until those exist, the acceptance claim "evidenced PR within the hour" is not testable.

### 5. The stated human gate cannot work with the phase-1 identity

The spec says the merge gate is "engineering department + company owner" at `SPEC.md:3-8`, but later says merge belongs to humans without defining whether approval means:

- one approval from any of Jacob, Engineer Two, or the Owner;
- one engineering approval plus the Owner's approval;
- or approval by all available approvers.

The current Fieldbook rule requires one approval, but "do not allow bypassing" and "approval of the most recent push" are off. The existing phase-1 publisher is Jacob's PAT. A PR opened by Jacob's GitHub account cannot be approved by Jacob. Today that means the factory either waits for Engineer Two or the Owner, or Jacob uses an administrator bypass - precisely the convention-only path the spec says GitHub should enforce.

PR #213 demonstrates the problem: it remains open and `REVIEW_REQUIRED` with Jacob as author.

Required revision:

- Resolve A33 into an exact, enforceable rule.
- Move the GitHub App or a dedicated non-human service identity into phase 1 so Jacob can review a factory-authored PR.
- Before the first live run, enable no-bypass and most-recent-push approval if the chosen policy requires them.
- Confirm Engineer Two and the Owner have the repository access needed to submit valid reviews.
- State who may merge after approval and whether one or two approvals are required.
- Do not count an admin-bypassed merge as a passing factory run.

## High-severity findings

### 6. The dashboard authorization scope is too broad and conflates submission with visibility

`SPEC.md:121-135` proposes the existing `reports` permission. That permission was created for agent-published reports, not software-request intake. The same user who can submit would also receive `GET /`, which lists requests, and `GET /request/<id>`, which displays verbatim request content and evidence.

This produces two problems:

- report viewers may gain access to internal engineering requests or screenshots unrelated to them;
- there is no distinction among submit, view-own, view-all, operate, and administer.

Required revision: add factory-specific permissions, at least `factory_submit` and `factory_admin`. Phase-1 request lists and operational state should be admin-only. If non-admin submitters are allowed, they should see only a success receipt until requester-facing authorization is deliberately built.

Caddy should also explicitly remove any client-supplied `X-Forwarded-Email` before copying the authenticated value, and the app should reject missing or malformed identities.

### 7. Upload security is asserted, not specified

`SPEC.md:118-130` says size/type limits are "enforced in types." Rust's type system does not verify that a PNG MIME declaration contains a safe PNG or that a filename cannot escape a directory.

The spec needs acceptance criteria for:

- canonical request IDs and filename generation, with no user filename used as a path;
- `O_EXCL`/create-new behavior and atomic rename;
- magic-byte detection, decoder pixel limits, and image re-encoding;
- archive and executable rejection;
- per-request and per-user quotas, request rate limits, and disk-full behavior;
- HTML/Markdown escaping, scriptable SVG rejection, and attachment `Content-Disposition`;
- CSP, frame protection, and no inline rendering of untrusted HTML;
- symlink and hard-link defense;
- malware scanning or a documented decision not to support arbitrary files.

Add adversarial upload fixtures for path traversal, double extensions, MIME spoofing, decompression bombs, malformed images, duplicate IDs, and concurrent submissions.

### 8. `gh pr view` during page rendering is an availability and injection hazard

`SPEC.md:131-133` calls GitHub at request time to derive state. At 20 estimated requests per week, every page load can create multiple network subprocesses. A GitHub outage, PAT problem, slow response, or rate limit degrades the whole dashboard. If any PR reference is built from queue text and passed through a shell, it can become command injection.

Required revision:

- Reconcile GitHub state into SQLite through a bounded CLI/library call with an argument vector, explicit timeout, output-size limit, and cached error state.
- Render from local state. A refresh action may request reconciliation, but the dashboard should not require live GitHub for every page.
- Fail closed on the 2-open-PR cap when GitHub state is unavailable.
- Serialize the cap check and PR creation under one publisher lock so two runs cannot both pass a time-of-check/time-of-use race.

### 9. The replay acceptance set is optimized for memorizing the pilot

`SPEC.md:140-149` requires three repeats of ALPHABETIZE and one fixture for each demotion. That can prove reproducibility on known prompts; it does not prove classification quality or resistance to the failures the factory is likely to encounter.

The golden test explicitly asks for a patch equivalent to PR #213, whose files and expected change are named throughout the playbook. A model can pass by pattern matching without demonstrating that it can locate the correct target. Repeating the same exposed case 3/3 does not measure false-positive risk.

Required revision:

- Keep ALPHABETIZE as a public smoke test.
- Add hidden positive cases in different report/dropdown implementations and hidden decoy files with similar labels.
- Add negative near-misses: `listOrder` is intentional routing priority, last-name ordering is requested, the dropdown includes a blank sentinel, values differ from labels, a shared getter has non-UI callers, and the desired sort requires locale/case handling.
- Add prompt-injection cases in email text, image OCR, filenames, source comments, and failing test output.
- Add state-machine cases: duplicate submit, crash before/after branch push, GitHub unavailable, preview unavailable, stale base SHA, PR cap race, and repair-loop exhaustion.
- Measure zero forbidden-lane publications and wrong-target rate, not only 3/3 success on known fixtures.
- Mutation-test the verifier by changing WHERE clauses, option values, membership, and sort keys, not only one intentionally wrong patch.

### 10. The ALPHABETIZE live acceptance test conflicts with the held PR

`SPEC.md:140-143` requires no duplicate PR and also requires one live run. PR #213 is currently open on `fix/alphabetize-salesperson-dropdowns`. The governing A35 instruction says it is held and should not be modified until the test decision is made.

The spec must choose one procedure before build acceptance:

- close PR #213 immediately before the live factory run and record the reason;
- reuse/adopt PR #213 without claiming the factory created it;
- or use a separate live request for publication while ALPHABETIZE remains dry-run only.

The current wording cannot be satisfied without either duplicating the PR or violating the hold.

### 11. Closure, deployed state, and outcome updates have no owner

`SPEC.md:92-94` says outcomes are filled at merge/close. `SPEC.md:125-133` displays merged, deployed, and closed states. There is no poller, webhook, scheduled reconciliation, or manual command in the stage contract that performs those transitions.

The dashboard cannot infer deployment from `gh pr view`. It must compare the merge SHA to the actual deployed Fieldbook SHA through an existing status-dashboard source or require an explicit human close action.

Required revision: add `factoryctl reconcile <id>` and `factoryctl close <id>` in phase 1, define exactly how deployed SHA is obtained, and append transactional events for merge, deploy, reply-drafted, and close. Automatic polling can remain phase 2.

### 12. The Rust choice is acceptable, but the estimate and supply-chain plan are not

`SPEC.md:156-182` treats Rust typing as a correctness guarantee and estimates two to three sessions for:

- a new toolchain;
- a verifier crate with mutation/self-tests;
- a multipart authenticated web app;
- Caddy and status-dashboard auth changes;
- subagent definitions and a skill;
- preview/browser integration;
- repository/queue migration;
- end-to-end replay and live PR acceptance.

Rust can prevent classes of memory and type errors. It cannot make authorization, path handling, state transitions, shell invocation, or product policy correct by itself. The current estimate creates pressure to skip the exact security details this review identifies.

Required revision:

- Pin the compiler with `rust-toolchain.toml` and commit `Cargo.lock`.
- Define dependency review and vulnerability checks (`cargo audit`/`cargo deny` or an equivalent reviewed policy).
- Define reproducible build, binary installation, rollback, checksum, and systemd deployment steps.
- Separate estimates for verifier, state layer, dashboard, auth/Caddy, preview evidence, and acceptance hardening.
- Budget at least one explicit threat-model/fuzzing session for the upload and path surfaces.

## Medium findings and specification inconsistencies

### 13. The sort skill's postcondition is underdefined

`SPEC.md:105-114` says labels equal their sorted copy and are a permutation of the before-set, but it does not define how the before-set is captured. A screenshot may not contain every option. A source query can differ from the rendered DOM. A shared getter can have callers with different presentation needs.

Define:

- whether sorting is by first name, last name, case-folded label, or database collation;
- treatment of blank/sentinel/disabled options and duplicate labels;
- preservation of option values, selected value, membership, and counts;
- how baseline DOM is captured at the base SHA;
- how shared callers are enumerated and checked;
- that changing `ORDER BY listOrder` is allowed only when evidence shows it is presentation order, not routing priority.

"Never drop listOrder from the DB" is too weak to protect the real risk. PR #213 did not drop the column; it stopped using that order in one query.

### 14. Acceptance criterion 3 refers to a nonexistent `bin/` layout

`SPEC.md:44-46` defines one Rust binary with subcommands. `SPEC.md:147-148` requires every `bin/` helper to fail on a wrong patch. Use one vocabulary and enumerate the verifier mutations each subcommand must reject.

### 15. The cap definition is incomplete

`SPEC.md:153-154` says helpers enforce 2 files, 50 lines, and 2 open PRs. Define:

- whether changed lines mean additions plus deletions;
- how renames, mode changes, generated/binary files, and whitespace-only changes count;
- whether newly added tests count toward the cap;
- whether the cap is measured against recorded base SHA or current master;
- fail-closed behavior when GitHub cannot confirm open PR count.

The open-PR cap is publisher state, not a patch-verifier subcommand.

### 16. Worktree ownership and cleanup are ambiguous

`SPEC.md:74-78` says worktrees are "under `/srv/orchestration/fieldbook` worktrees." The existing Fieldbook checkout is a shared read cache that other agents and dashboard version checks rely on. A nested worktree or a branch left checked out there can dirty or confuse that cache.

Use a dedicated bare clone and worktree root under `/var/lib/patchyard/` or `/srv/patchyard-worktrees/`. Record base SHA, fetch before branching, refuse an existing branch unless it belongs to the same request, and define cleanup after failure, close, and merge.

### 17. The spec does not define model, prompt, or artifact provenance

The ledger records tokens and turns but not the exact model identifier, CLI/runtime version, constitution hash, rubric hash, skill hash, prompt template hash, verifier binary hash, or base tree hash. Without these, a 3/3 replay cannot be reproduced or compared after a tool update.

Add all of them to each run record.

## Revised phase-1 minimum

The smallest phase 1 I would approve is:

```text
factory.example.com
  -> Caddy auth
  -> factory-web (dedicated user)
  -> SQLite request/event ledger + private artifact store

Engineer runs /factory <id>
  -> deterministic supervisor claims request
  -> read-only triage
  -> isolated credential-free implement worker emits patch
  -> clean deterministic verifier + tree hash
  -> outer publisher uses Patchyard Software Factory GitHub App
  -> draft PR
  -> CI + exact-SHA preview + DOM/screenshot evidence
  -> ready for one precisely defined human approval
  -> existing production deploy gate
  -> manual reconcile/close command updates ledger
```

This still leaves mailbox polling, automatic reconciliation, automatic requester notifications, cross-family review, and the kill-switch UI for phase 2. It moves only the security and state foundations that phase 1 already needs.

## Required spec changes before Jacob's build approval

1. Remove worker isolation, GitHub App identity, and SQLite from the phase-2-only non-goals.
2. Replace subagent-tool restrictions as the claimed security boundary with an OS-enforced worker and verifier boundary.
3. Run the dashboard as `factory-web`, add factory-specific authorization, and specify upload hardening.
4. Move live queue/artifacts out of Git and define retention.
5. Add transactional state, locks, idempotency, retry, and recovery semantics.
6. Define the draft-PR to CI to preview to ready lifecycle and artifact hosting.
7. Resolve the exact approval rule and phase-1 PR identity.
8. Resolve PR #213's disposition before the live golden-path test.
9. Expand acceptance from exposed replay repetition to hidden near-miss, injection, concurrency, and failure cases.
10. Replace the two-to-three-session estimate with component estimates and explicit security/reliability work.

After those changes, the spec's narrow scope and verification-first approach are strong enough to justify a build. Without them, phase 1 would create a polished interface around the exact trust and concurrency risks the later phases are supposed to solve.
