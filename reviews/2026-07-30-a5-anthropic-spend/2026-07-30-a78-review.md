## Blockers

### A78-1 - The initial attempt tainted the worker, but the record omits its replacement

Severity: High - evidence integrity and containment.

The runtime writes `BOUNDARY_TAINTED` whenever a provider-qualification run exits nonzero. The initial failure record proves such a run ended at `result-filesystem-validation` with status 1. Requirement 1 and the repaired spend run later required a marker-free worker, so the marker was cleared or the worker was replaced. The initial record has no containment block, and its checker freezes a shape that cannot record the missing event.

Verification criterion: inspect the worker filesystem/journal and record the initial marker plus the authorized clearing or replacement action. Do not claim no marker was written without evidence that contradicts the committed runtime.

### A78-2 - No evidence establishes that the $1.00 cap was active during the repaired probe

Severity: High - evidence integrity and overclaiming.

The committed operator observations put the $50.00 restoration at 02:07Z, fourteen minutes before the journaled 02:21:34Z to 02:21:53Z run. The repository finalizer normally rejects this ordering. Ignoring the timestamps prevents a false ordering assertion but leaves the cap value at probe time unproved.

Verification criterion: reconcile the Console observations against a wall-clock source. If that cannot be done, state that the cap in force during the probe is not established by committed evidence.

### A78-3 - The `$0` incremental repair cost was observed too early to call settled

Severity: High - cost evidence.

The after-repair Cost Report snapshot was taken 4 minutes 17 seconds after the failure. The initial attempt's cost took about 2 hours 51 minutes to appear. Equality between the before and four-minute after snapshots therefore proves only that no new cost had reported yet. It does not prove that the repaired request incurred $0.

The $6.68168 figure is exact initial spend above the temporary cap, but it is not an A113 overshoot at denial because no attributable denial was captured.

Verification criterion: make a later read-only Cost Report observation after the settlement window and qualify the figure's name.

### A78-4 - The repair narrowed the denial predicate without diagnosing the rejected shape

Severity: Medium-High - fail-closed repair design.

The repair added exact top-level and nested key-set equality checks. They do not address the diagnosed initial failure, and they reject an otherwise valid attributable provider error with any compatible extra field. The failure path exports only `anthropic-spend-unexpected-response-400`, so a provider-contract extension and an unrelated 400 are indistinguishable.

Verification criterion: use required-key containment while preserving type, message, and request-ID checks; export only a credential-free rejected-shape descriptor; bind an extra-field case in test. No provider request is needed.

### A78-5 - Post-denial failures are mislabeled as `denial-not-observed`

Severity: Medium - A114 record honesty.

After the denial envelope predicate succeeds, request-ID equality, server-date parsing, nonempty evidence checks, credential deletion, and directory removal can still fail while `FAILURE` remains `anthropic-spend-denial-not-observed`. A valid denial followed by one of those failures would therefore publish a false provider outcome.

Verification criterion: assign a distinct post-denial failure state immediately after the envelope is accepted, allowlist it, and test the assignment order.

## Non-blocking observations

### A78-6 - The guest retains the bearer on spend-branch failure paths

Severity: Medium.

The spend branch removes the curl configuration and capability only after a qualifying denial is completely parsed. Transport, 200, unexpected-response, and post-denial parsing failures write `/result/status` while the bearer remains in guest tmpfs. The launcher still prevents the credential from crossing the accepted result boundary and the VM is force-rebooted, but the stated delete-before-result invariant is false on failure.

### A78-7 - The documentation overstates workspace-cap binding

Severity: Medium.

A Console UI and client-payload inspection prove that a lower value is accepted and displayed, not that the server enforces it independently. The only initial live test accepted $7.68 of spend against a displayed $1.00 cap. The binding statement should be an inference, with enforcement timing explicitly unproved.

### A78-8 - The checker freezes escalation records and makes them mutually exclusive with success

Severity: Medium.

Under the current checker, a future success requires deleting the terminal failure record or changing the checker. Both failure records are exact-shape freezes, so correcting them also requires a checker change. A78 recommends a reviewed reauthorization field and a comment distinguishing byte freezes from independent verification.

### A78-9 - Static one-probe and teardown-order tests have gaps

Severity: Low.

The spend checker catches `for ATTEMPT` and `sleep`, but not `while`, `until`, `xargs`, or `curl --retry`. It counts endpoint literals rather than invocations. The A114 test checks that `rc=$(final_exit_status "$rc")` exists but not that it occurs after residue counting, so hoisting it can restore the defect while leaving the test green.

### A78-10 - Several teardown operations can fail without changing the final status

Severity: Low, partly pre-existing.

Under `set +e`, output purge, ownership/mode repair, and `write_terminal` may fail without setting a residue counter or `TEARDOWN_COMPLETE=false`. The launcher can then exit 0, including when no terminal record was written.

### A78-11 - The two intermediate feature commits fail their own issuance digest gate

Severity: Low.

`105a3c6` and `84bdf99` each contain requirement 1 evidence for the prior host-contract source. Only PR head `038fd9d` reconciles the evidence and current source. CI tests the PR head, so this is a bisectability observation rather than a merge-gate failure.
